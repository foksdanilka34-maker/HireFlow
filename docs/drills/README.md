# Проверка устойчивости HireFlow

Нагрузочный тест k6 и учения со сбоями на локальном стенде (`make up`). По итогам учений пишется постмортем
(шаблон — [docs/postmortems](../postmortems/README.md)). Описание — design.md, раздел 16.

Учения:
- [Пауза PostgreSQL под нагрузкой](postgres-pause.md) — `make drill`.

## Нагрузочный тест

Сценарий — `load/hireflow.js`, сервис `k6` в профиле `load` docker-compose. Нагружается путь бота без откликов:
`GET /vacancies?status=open`, затем `POST /candidates/{telegramId}/matches` с резюме `load/resume.pdf`
(данные вымышленные). Запросы идут через Caddy (`http://web/api`), как настоящий трафик, с ключом бота из `.env`.

Запуск на поднятом стенде:

```
make load                       # 10 итераций/с, разгон 1 мин + удержание 4 мин
make load RATE=2 DURATION=20s   # короткая проверка
```

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `RATE` | 10 | итераций в секунду (одна итерация — два запроса) |
| `DURATION` | 4m | удержание после минуты разгона |

Пороги — SLO из design.md §16: `http_req_failed` меньше 0,5%, `http_req_duration` p(95) меньше 1 с. Порог не
выполнен — k6 завершается с ненулевым кодом. Результат — сводка k6 в консоли, влияние на систему — дашборд
«HireFlow» в Grafana (http://localhost:3000).

Тест не создаёт откликов и уведомлений: бот никому не пишет. Подбор пишет только строку лимита загрузок
в `resume_uploads` (хэш файла и время, не ПД) — не больше одной на виртуального пользователя, Telegram ID
из тестового диапазона от `990000000000`. Файл всегда один, поэтому лимит загрузок (429) не срабатывает.
Очистка — в [postgres-pause.md](postgres-pause.md#очистка).

Если открытых вакансий нет, k6 предупреждает об этом: подбору не с чем сравнивать, но извлечение текста
из резюме всё равно нагружается.
