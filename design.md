# HireFlow — дизайн системы

## 1. Цель

Система первичного отбора кандидатов. Кандидат присылает резюме Telegram-боту, система подбирает подходящие открытые вакансии, кандидат выбирает вакансию и откликается. Дальше система автоматически проверяет резюме, собирает уточняющие ответы и передаёт подходящих кандидатов рекрутеру. Решение о приглашении на созвон всегда принимает рекрутер.

## 2. Пользователи

- **Кандидат** — работает только через Telegram-бота. Кнопок нет: только текст и файлы; из команд — `/start`, `/help`, `/status`.
- **Рекрутер** — работает через веб-интерфейс: создаёт вакансии, видит кандидатов на проверке, принимает решения.

## 3. Компоненты

| Компонент | Технология | Назначение |
|---|---|---|
| `HireFlow.Api` | ASP.NET Core, .NET 10 | Вся бизнес-логика, единая точка доступа к данным и проверки прав |
| Фоновые обработчики | Hosted services внутри API | Скрининг, вызовы ИИ, подготовка уведомлений |
| `HireFlow.Bot` | Worker service, Telegram Bot API | Интерфейс кандидата. Ходит только в API |
| `HireFlow.Web` | Blazor WebAssembly, Bootstrap | Интерфейс рекрутера в браузере. Ходит только в HTTP API |
| PostgreSQL | EF Core | Данные и очередь задач |
| S3-совместимое хранилище | MinIO или аналог, доступ через S3-клиент | Файлы резюме. В базе — только ключ файла и метаданные |
| Локальная модель ИИ | llama.cpp (`llama-server`), instruct-модель до 4B | Рекомендации по пограничным откликам и ответам (раздел 6). Ходит к ней только API |

Брокер сообщений не используется: для одного API и двух клиентов он избыточен. Надёжность асинхронной обработки обеспечивается очередью и outbox в PostgreSQL.

```
Кандидат ── Telegram ── HireFlow.Bot ──┐
                                       ├── HireFlow.Api ── PostgreSQL
Рекрутер ── браузер ── HireFlow.Web ──┘        │
                                               ├── S3-хранилище
                                               └── llama.cpp, локальная модель (пограничные случаи и ответы на вопросы)
```

## 4. Воронка и статусы отклика

До отклика: резюме → подбор вакансий (раздел 5) → кандидат выбирает вакансию → создаётся отклик.

```
Принят → Скрининг ─┬─ Не прошёл ──────────────────────────→ Отказ (автоматически)
                   ├─ Пограничный → Проверка ИИ ─┬─ Прошёл → Уточняющие вопросы
                   │                             └─ Не прошёл / ИИ недоступен → Проверка рекрутером (с пометкой)
                   └─ Прошёл ─────────────────────────────→ Уточняющие вопросы

Уточняющие вопросы ─┬─ Ответы получены → Проверка ответов ИИ → Проверка рекрутером (с пометкой ИИ)
                    └─ Нет ответа N дней → Истёк

Проверка рекрутером ─┬─ Пригласить на созвон
                     └─ Отказ
```

Правила:
- Автоматический отказ — только при явном несоответствии правилам скрининга. ИИ не отказывает сам.
- Файл проверяется при загрузке, до создания отклика (раздел 5). Неподходящий формат или файл без текста — не отказ: бот просит прислать другой файл, отклик не создаётся.
- Каждая смена статуса записывается в историю: кто (система, ИИ, рекрутер), когда, почему.
- Скрининг по правилам выполняется сразу при создании отклика. Пока нет этапов 3 и 4, «прошёл» и «пограничный» сразу переходят в «Проверку рекрутером»; пограничность видна по вердикту скрининга.
- Автоматический отказ и отказ рекрутера — разные статусы, чтобы автоотказы можно было выбрать простым фильтром.
- Статусы в API и базе: `received`, `recruiter_review`, `auto_rejected`, `invited`, `rejected`; статусы этапов 3–4 добавятся вместе с ними.

## 5. Скрининг и подбор вакансий по правилам (ATS)

Входные данные: текст резюме, опыт (из резюме или ответ кандидата в боте), требования вакансии.

**Приём файла** — до подбора и до отклика:
- форматы PDF и DOCX, размер до 10 МБ;
- формат определяется по содержимому файла (PDF начинается с `%PDF`, DOCX — zip-архив), а не по расширению;
- старый `.doc`, скан без текста или повреждённый файл → бот просит прислать другой файл.

**Проверки:**
- **Обязательные навыки:** все должны найтись в тексте, с учётом синонимов из вакансии (например, «C#», «.NET», «dotnet»). Среди обязательных должен быть хотя бы один навык, характерный именно для этой роли (например, «автотесты» для QA, «ASP.NET» для разработчика), иначе вакансии разных ролей начнут пересекаться при подборе.
- **Желательные навыки:** добавляют баллы.
- **Опыт:** берётся из резюме только по явной формулировке: «Опыт работы — 5 лет 3 месяца», «опыт работы: 5 лет», «более 3 лет опыта», «3+ года опыта», «5+ years of experience», «Experience: 5 years». Месяцы отбрасываются, из нескольких формулировок берётся первая. Диапазоны дат («2019–2023») **не суммируются**: ошибка в расчёте дала бы неверный автоотказ. Явной формулировки нет (или число вне 0–50) → бот спрашивает опыт числом. Ответ кандидата точнее извлечённого и используется в первую очередь.

**Поиск навыка в тексте** (по названию и синонимам):
- без учёта регистра, «ё» = «е», кириллическая «с» в «С#» и «С++» считается латинской;
- целым словом: до и после навыка нет буквы, цифры, «#» или «+». Поэтому «C» не находится внутри «C#», а «SQL» — внутри «PostgreSQL» (для этого есть синонимы);
- пробел или дефис в навыке совпадает с пробелом, дефисом или их отсутствием: «Spring Boot» = «SpringBoot» = «spring-boot»;
- «*» в конце навыка или синонима — любое окончание: «автотест*» найдёт «автотесты», «автотестов», «автотестирование».

**Балл** — по **доле** найденных навыков, а не по их количеству: 80 × доля обязательных + 20 × доля желательных (если желательных нет — 100 × доля обязательных). Опыт в балл не входит: его нехватка считается ещё одним недостающим требованием.

Результат: балл 0–100 и причины — каких навыков не хватает и достаточно ли опыта.
- Все обязательные навыки найдены, опыта достаточно и балл ≥ порога → **прошёл**.
- Иначе, если не хватает ровно одного требования (навыка или опыта) или балл ≥ порога − ширины зоны → **пограничный**.
- Иначе → **не прошёл**.

**Ограничения правил:** контекст («хочу изучить Docker») не понимается, сокращения без синонимов («Postgres») не находятся, навыки картинками в резюме не видны. Это компенсируют проверка ИИ пограничных откликов и решение рекрутера.

Порог и ширина пограничной зоны задаются в вакансии; ширина по умолчанию — 10 баллов.

### Подбор вакансий

Тот же движок оценки, запущенный по резюме против всех открытых вакансий ещё до отклика.

- Показываются только вакансии с результатом «прошёл». Пограничные в подборе не показываются: показать вакансию — значит пригласить откликнуться.
- Не показываются вакансии, на которые кандидат уже откликался. На этапе 5 правило уточняется: активный отклик или действующая заморозка (раздел 12).
- Сортировка по баллу, не больше 3 вакансий на странице, дальше — «ещё» (текстом).
- Направления кандидата не спрашиваем: сортировка только по баллу.
- Ничего не подошло → «сейчас подходящих нет» и подсказка написать «все», чтобы увидеть все открытые вакансии.
- Кандидату не показываются баллы и причины — только список вакансий.
- ИИ не используется. Резюме обрабатывается в памяти и не сохраняется (раздел 15).
- **Лимит загрузок**, чтобы нельзя было подобрать критерии перебором: не больше 3 разных файлов (по SHA-256) за скользящие 24 часа на Telegram ID (IP боту недоступен). Повтор того же файла и повторный подбор с опытом лимит не тратят. Лимит строгий при последовательных запросах (бот обрабатывает кандидата по порядку). Новый файл сверх лимита → `429`, подбор не выполняется; бот отвечает «Сегодня вы уже прислали 3 разных резюме…». Для лимита хранятся только Telegram ID, хэш файла и время (раздел 15).

## 6. Проверка ИИ

Применяется в двух местах:
- **пограничные отклики** после скрининга по правилам;
- **ответы на уточняющие вопросы** (раздел 7).

Подбор вакансий (раздел 5) ИИ не использует.

В обоих случаях ИИ выносит только рекомендацию, итоговое решение — за рекрутером.

- **Обезличивание перед отправкой:** удаляются имя, телефон, почта, ссылки, дата рождения, адрес. Отправляются только фрагменты, относящиеся к навыкам и опыту.
- **Строгий формат ответа:** модель возвращает JSON с рекомендацией (`pass` / `review`), оценкой и объяснением. Ответ, не прошедший валидацию, считается неуспешным.
- **Текст кандидата — недоверенные данные.** Инструкции внутри резюме или ответов игнорируются, ответ модели никогда не исполняется как команда.
- **ИИ только рекомендует.** Отрицательная рекомендация не приводит к отказу, отклик уходит рекрутеру с пометкой и объяснением.
- **Сбои:** таймаут, ограниченное число повторов с паузой; если ИИ недоступен — отклик уходит рекрутеру.
- Сохраняются версия промпта, ответ модели и время ответа.

### Модель и сервер

- **Сервер:** llama.cpp (`llama-server`) на той же машине или в той же сети, что и API. Наружу не публикуется. API
  обращается к нему по HTTP (OpenAI-совместимый `/v1/chat/completions`); адрес, имя модели, таймаут и число повторов —
  в настройках. В Application — интерфейс (например, `IAiReviewer`), реализация в Infrastructure, поэтому модель и
  сервер меняются без правок бизнес-логики.
- **Модель:** генеративная instruct-модель размером до 4B с хорошей поддержкой русского языка, квантованная (GGUF).
  Модели эмбеддингов (например, семейства EmbeddingGemma) для этой задачи не подходят: они не формулируют рекомендацию
  и объяснение. Конкретная модель выбирается прогоном на 30–50 обезличенных резюме с известными решениями рекрутера.
- **Вход — текст, а не файлы.** Текст из PDF и DOCX извлекает API (раздел 5), модели передаются только обезличенные
  фрагменты про навыки и опыт. Умение модели «читать PDF» не требуется. Сканы без текста по-прежнему не принимаются;
  если понадобятся — через OCR, а не через мультимодальную модель.
- **Строгий JSON:** ответ ограничивается JSON-схемой на стороне сервера (`response_format` / грамматика llama.cpp)
  и дополнительно валидируется в API.
- **Вызов асинхронный:** через очередь фоновых задач (раздел 11), а не внутри HTTP-запроса создания отклика.
- **Резервного алгоритма нет и он не нужен:** решение «прошёл / пограничный / не прошёл» уже принимает скрининг по
  правилам (раздел 5); ИИ смотрит только пограничные. Если модель недоступна или ответ не прошёл валидацию, отклик
  уходит рекрутеру с пометкой «ИИ недоступен». Отказать кандидату из-за недоступности ИИ нельзя.
- **Вместе с ответом** сохраняются имя модели и версия промпта — чтобы сравнивать модели и промпты.
- **Возможное улучшение подбора (не этап 3):** модель эмбеддингов для похожих навыков, которых нет в синонимах
  («Postgres» ≈ «PostgreSQL»). Только повышает вердикт (не прошёл → пограничный), отказывать не может.

## 7. Уточняющие вопросы

После успешного скрининга бот задаёт вопросы из вакансии: ожидания по зарплате, формат работы, дата выхода, количество часов и т. п. Вопросы задаются в вакансии рекрутером, к каждому можно указать ожидаемый ответ или критерий (например, вилку зарплаты).

Сопроводительного письма в системе нет. Если рекрутеру по вакансии нужна мотивация кандидата, он добавляет вопрос, например «Почему вам интересна эта вакансия? 2–3 предложения».

Ответы проверяет ИИ: сравнивает с критериями вакансии и ставит пометку — «соответствует», «есть расхождения» (с перечнем, например «ожидания по зарплате выше вилки») или «требует внимания». Отклик в любом случае уходит рекрутеру, пометка лишь помогает ему расставить приоритеты. Ответы, как и резюме, отправляются в ИИ без персональных данных.

Если кандидат не ответил за N дней, отклик переходит в «Истёк».

## 8. Интерфейс рекрутера

Кабинет — Blazor WebAssembly с Bootstrap, работает целиком в браузере и ходит в API напрямую, с cookie-сессией. Адрес API и имя бота (`BotUsername`) задаются в `wwwroot/appsettings.json` — этот файл публичный, секретов в нём нет. Даты показываются в локальном времени браузера.

- **Вход по логину и паролю** — интерфейс содержит персональные данные. После входа API выдаёт cookie-сессию на 8 часов со скользящим продлением; попытки входа ограничены по IP (5 в минуту, сверх — 429), без блокировки аккаунта. Регистрации нет: рекрутеры заводятся консольной командой `make recruiter LOGIN=<логин>` (она же меняет пароль). Ролей нет, все рекрутеры равны.
- **Вакансии:** создание, редактирование, открытие, закрытие, архив; удаление — только если на вакансию нет откликов. Направление (с подсказкой уже существующих), требования, синонимы навыков, порог, вопросы. Подсказка: «добавьте навык, характерный для этой роли».
- **Ссылка на вакансию:** кнопка «скопировать ссылку» вида `t.me/<бот>?start=<id вакансии без дефисов>` для публикации на сайте и в каналах.
- **Очередь на проверку:** отклики в статусе «Проверка рекрутером», отсортированные по баллу (высокий сверху; при равном — кто дольше ждёт), с фильтрами по вакансии и пометкам (на этапе 1 — «только пограничные»).
- **Все отклики:** общий список (новые сверху) с фильтрами по вакансии и статусу.
- **Карточка отклика:** резюме, ответы на вопросы, балл и причины, рекомендация ИИ, история статусов, пометки (например, «номер совпадает с другим кандидатом»). PDF-резюме показывается во встроенном просмотрщике браузера, docx — сохранённым текстом (плюс ссылка на скачивание файла). После решения рекрутер остаётся в карточке, она обновляется.
- **Решение:** «Пригласить на созвон» или «Отказ» с комментарием (комментарий необязателен).
- Автоматические отказы доступны в отдельном списке для выборочной проверки качества скрининга. Если рекрутер не согласен с системой, он может пригласить кандидата из автоотказа; ещё не отправленное уведомление об отказе при этом отменяется. Если отказ уже отправлен кандидату, карточка предупреждает об этом и просит подтвердить приглашение.

## 9. Telegram-бот

**Кнопок нет совсем:** ни inline-, ни reply-клавиатур, ни `request_contact`. Бот понимает текст, файлы и команды `/start`, `/help`, `/status`. Всё, что раньше было кнопкой, — текст: номер вакансии, «ещё», «все», «да», «нет».

- **Два входа:** ссылка из вакансии (`t.me/<бот>?start=<id вакансии>`) или просто открыть бота. Дальше сценарий один:
  ```
  /start → приветствие → «Пришлите резюме (PDF или DOCX)»
    (по ссылке: «Вы откликаетесь на «<вакансия>». Пришлите резюме»;
     вакансия закрыта или не найдена: «Набор на эту вакансию закрыт. Пришлите резюме — подберём другие»)
  Резюме (файл)
  Опыт: из резюме (раздел 5); не нашли → «Сколько лет у вас опыта? Напишите число»
  Подбор (раздел 5)
    до 3 вакансий «1. <название> (<направление>)», «Напишите номер»; «ещё» — следующие 3
    ничего не подошло → «Напишите «все»» — все открытые вакансии, выбор тоже номером
    пришёл по ссылке и вакансия подходит → «Откликнуться? да/нет»
    пришёл по ссылке, но вакансия не подходит → подходящие + «0 — всё равно откликнуться»
  Выбор вакансии номером → при первом отклике и отсутствии телефона в резюме «Напишите номер для связи»
    → «Отклик принят, сообщим результат»
  ```
- **Шаги диалога** (`BotSession.step`): `awaiting_resume`, `awaiting_experience`, `choosing_vacancy`, `confirming_linked`, `awaiting_phone`. Новый файл на любом шаге начинает подбор заново.
- **Команды:** `/start` сбрасывает диалог; `/help` объясняет бота и что ожидается на текущем шаге; `/status` показывает отклики кандидата. `/help` и `/status` шаг не меняют. Текст, фото и стикеры на шаге ожидания резюме дают подсказку «Пришлите резюме файлом PDF или DOCX».
- **Закрытые вакансии и вакансии в архиве** бот не показывает и не предлагает, в том числе по ссылке. Если вакансию закрыли, пока кандидат откликался, бот проверит это до вопроса о телефоне (API тоже отклонит отклик), скажет «набор уже закрыт» и покажет подходящие. Повторный отклик → «Вы уже откликались на «<вакансия>», статус: …».
- **Имя и телефон:** имя берётся из профиля Telegram (`first_name` + `last_name`). Телефон берётся из резюме (первый фрагмент, похожий на номер; годы, даты и индексы не считаются), иначе бот спрашивает его текстом. Номер приводится к формату E.164: `+` и от 7 до 15 цифр. Принадлежность номера кандидату не проверяется.
- **Создание кандидата:** при первом отклике, внутри `POST /applications`, в одной транзакции с откликом: Telegram ID, имя и телефон. У существующего кандидата имя и телефон не перезаписываются.
- **Согласие на обработку ПД** перед обработкой резюме — на этапе 6 (раздел 15).
- **Состояние диалога** хранится в базе (через API): шаг, вакансия по ссылке, черновик (`file_id` резюме в Telegram, имя файла, опыт, найден ли телефон в резюме, список id вакансий подбора, страница). Телефон и текст резюме в черновик не пишутся. Перезапуск бота ничего не теряет. Сообщения одного пользователя обрабатываются строго по очереди, разных пользователей — параллельно (N очередей по Telegram ID, настройка `Bot:Workers`), чтобы медленный ход одного кандидата не задерживал остальных. Если очередь переполнена (100 сообщений), новые сообщения кандидата отбрасываются. При остановке бот дообрабатывает уже полученные сообщения в пределах таймаута остановки 60 с.
- **Статус:** кандидат может в любой момент посмотреть статус своих откликов (`/status`). Он видит три статуса: «На рассмотрении», «Приглашение на созвон», «Отказ». Об отказе кандидат узнаёт только после отправки уведомления (раздел 10), а автоотказ и отказ рекрутера для него выглядят одинаково.
- **Ошибки:** API недоступен или ответил 5xx → «Что-то пошло не так, попробуйте ещё раз через минуту», шаг не меняется. Если отклик уже создан, а сохранить диалог не удалось, кандидат всё равно видит «Отклик принят» (сбой только логируется).
- **Тексты сообщений** кандидату составляет бот по типу уведомления. В логи не пишутся текст сообщений, имена файлов, телефоны и содержимое резюме.

## 10. Уведомления и задержки (outbox)

- Уведомление записывается в таблицу `notifications` в той же транзакции, что и смена статуса. Создаёт его сам отклик при смене статуса, поэтому забыть уведомление нельзя.
- Типы: `invited` (уходит сразу) и `rejected` (автоотказ и отказ рекрутера). В уведомлении хранится тип, а не текст: текст составляет бот.
- Поле `send_after` задаёт задержку: отказ отправляется не раньше чем через `Notifications:RejectionDelay` (4 часа; в разработке — 1 минута).
- Бот периодически запрашивает у API уведомления, у которых наступило время, отправляет их и подтверждает отправку (`sent`) или сообщает об ошибке (`failed`).
- Неудачная отправка повторяется через 2, 4, 8… минут; после 5 неудач уведомление помечается как ошибочное.
- Приглашение из автоотказа отменяет ещё не отправленный отказ.
- Доставка «хотя бы один раз»: если бот упадёт между отправкой и подтверждением, сообщение уйдёт повторно.

## 11. Очередь фоновых задач

- Задачи (проверка ИИ) хранятся в PostgreSQL. Скрининг по правилам в очередь не попадает: он быстрый, без внешних вызовов и выполняется сразу при создании отклика. Очередь появляется на этапе 3 вместе с ИИ.
- Обработчик забирает задачи запросом `SELECT … FOR UPDATE SKIP LOCKED`, поэтому несколько экземпляров не возьмут одну задачу.
- Повтор при ошибке с растущей паузой, ограниченное число попыток, после чего задача помечается как ошибочная и видна в мониторинге.
- Перезагрузка API ничего не теряет.

## 12. Повторные отклики и заморозка

- **Один активный отклик** на вакансию от кандидата: при повторе бот показывает текущий статус.
- **Тот же файл:** определяется по `file_unique_id` из Telegram (он постоянен, в отличие от `file_id`) и хэшу содержимого.
- **Заморозка после отказа:** повторный отклик на ту же вакансию невозможен в течение срока, заданного в вакансии; по умолчанию 3 месяца.
- **Идентификация кандидата:** Telegram ID — точная идентификация, на ней держатся «один активный отклик» и заморозка. Телефон кандидата не уникален: совпадение номера с другим Telegram-аккаунтом может означать как того же человека с новым аккаунтом, так и нового владельца переназначенного номера, поэтому оно не блокирует, а помечает отклик для рекрутера. Совпадение только по имени и опыту тоже лишь помечает отклик (возможны однофамильцы). Телефон, найденный в резюме, используется как телефон кандидата при первом отклике (раздел 9), но с другими кандидатами не сверяется; прочие контакты из резюме не сверяются.

## 13. Модель данных

- **Vacancy** — название, направление, описание, статус (открыта / закрыта / в архиве), требования (навыки с синонимами, опыт, порог, пограничная зона), вопросы, срок заморозки.
- **Candidate** — Telegram ID (уникальный), имя, телефон (E.164, не уникальный), дата согласия (этап 6).
- **Application** — вакансия, кандидат, ключ файла, хэш файла, `file_unique_id`, текст резюме, опыт, балл, причины, рекомендация ИИ, ответы на вопросы, статус, даты.
- **ApplicationStatusHistory** — отклик, старый и новый статус, кто изменил, причина, время; для решений рекрутера — `recruiter_id`.
- **BackgroundJob** — тип, ссылка на отклик, статус, попытки, время следующей попытки, ошибка.
- **Notification** — отклик, тип (`invited` / `rejected`), `send_after`, статус (`pending` / `sent` / `failed` / `cancelled`), попытки, последняя ошибка.
- **BotSession** — Telegram ID (уникальный), шаг диалога, вакансия по ссылке, черновик `draft` (jsonb-объект до 8 КБ: `resume_file_id`, `resume_file_name`, `years_of_experience`, `phone_found`, `vacancy_ids`, `page`, `pending_vacancy_id`), время обновления. API не интерпретирует шаг и черновик — это состояние бота.
- **ResumeUpload** — Telegram ID, SHA-256 хэш файла, время загрузки; уникален по (Telegram ID, хэш). Нужен только для лимита загрузок (раздел 5); записи старше 24 часов удаляются при следующей загрузке этого кандидата, общая очистка — этап 6.
- **Recruiter** — логин (уникальный, в нижнем регистре), хэш пароля (PBKDF2), дата создания.

## 14. API

| Метод | Путь | Кто использует |
|---|---|---|
| `POST` | `/auth/login`, `/auth/logout` | Web: вход (cookie) и выход |
| `GET` | `/auth/me` | Web: текущий рекрутер |
| `GET/POST/PUT/DELETE` | `/vacancies` | Web; бот — только чтение открытых (`?status=open`). DELETE — только без откликов |
| `POST` | `/vacancies/{id}/open`, `/close`, `/archive`, `/unarchive` | Web |
| `GET/PUT` | `/candidates/{telegramId}` | Бот: узнать, известен ли кандидат; PUT — служебное обновление имени и телефона (бот кандидата не создаёт) |
| `POST` | `/candidates/{telegramId}/matches` | Бот: файл + опыт (необязателен) → `{ yearsOfExperience, experienceRequired, phoneFound, vacancies }`; сохраняет только хэш файла для лимита; новый файл сверх 3 разных за 24 ч → `429`. Опыт не передан → ищется в резюме, не нашёлся → `experienceRequired = true` и пустой список |
| `POST` | `/applications` | Бот: создание отклика (файл, вакансия, опыт, `name`, необязательный `phone`); при первом отклике создаёт кандидата |
| `GET` | `/applications?vacancyId=&status=` | Web |
| `GET` | `/applications/{id}` | Web: карточка с вакансией, именем и телефоном кандидата, историей (с логином рекрутера), `resumeFormat` (`pdf`/`docx`) и `rejectionSent` (отказ уже отправлен кандидату) |
| `GET` | `/applications/{id}/resume` | Web: скачать файл резюме; `?inline=true` для PDF — `Content-Disposition: inline` (просмотр в браузере). Всегда `X-Content-Type-Options: nosniff` |
| `GET` | `/applications/{id}/resume/text` | Web: сохранённый текст резюме `{ text }` |
| `POST` | `/applications/{id}/answers` | Бот |
| `POST` | `/applications/{id}/decision` | Web: приглашение или отказ |
| `GET` | `/candidates/{telegramId}/applications` | Бот |
| `GET/PUT` | `/bot-sessions/{telegramId}` | Бот |
| `GET` | `/internal/notifications/due` | Бот |
| `POST` | `/internal/notifications/{id}/sent`, `/failed` | Бот |
| `GET` | `/health/live`, `/health/ready`, `/metrics` | Мониторинг |

Доступ: рекрутер — по cookie-сессии после `POST /auth/login`; бот — по служебному ключу в заголовке `X-Api-Key` (настройка `BotApi:ApiKey`, хранится в user secrets или переменной окружения `BotApi__ApiKey`, в репозиторий не попадает; без ключа API не стартует). Маршрут без явной политики по умолчанию закрыт сессией рекрутера. Только ключ бота: `/candidates`, `POST /applications`, `/bot-sessions`, `/internal/notifications`. Сессия или ключ: `GET /vacancies` и `GET /vacancies/{id}`. Без входа: `/`, `/health`, `/auth/login`, `/auth/logout`, OpenAPI в Development. Остальное — только сессия рекрутера. Нет нужных учётных данных (в том числе ключ бота на маршруте рекрутера и cookie на маршруте бота) или неверный ключ → 401. CORS разрешён только адресам кабинета из `Web:Origins` (с credentials, чтобы браузер отправлял cookie); пустой список — CORS ничего не разрешает.

## 15. Персональные данные

Согласие, срок хранения и удаление по запросу реализуются на этапе 6; остальные пункты соблюдаются с самого начала.

- Согласие кандидата — до обработки резюме: пока согласия нет, бот не скачивает файл, а API не принимает резюме.
- Подбор вакансий обрабатывает резюме в памяти; для лимита загрузок сохраняются только Telegram ID, хэш файла и время (не содержимое и не текст), записи старше 24 часов удаляются при следующей загрузке этого кандидата (общая очистка — этап 6); резюме хранится, только если кандидат откликнулся.
- Текст резюме и ответов не пишется в логи.
- Пароль рекрутера не хранится и не логируется — только его хэш; хэш не возвращается в ответах, логин при неудачном входе не логируется.
- В ИИ уходят только обезличенные фрагменты.
- Срок хранения данных и удаление по запросу кандидата.

## 16. Эксплуатация (SRE)

- **Запуск:** Docker, docker compose для всего стенда.
- **CI:** GitHub Actions — сборка, тесты, образы.
- **Метрики:** отклики по статусам, длительность скрининга, длина очереди задач, задержка и ошибки ИИ, неотправленные уведомления, ошибки бота.
- **Трейсы:** OpenTelemetry, сквозной путь бот → API → фоновый обработчик → ИИ.
- **Логи:** структурные, в Loki.
- **SLO и алерты:** например, 99% откликов проходят скрининг быстрее 1 минуты; алерты на нарушение SLO, рост очереди, недоступность ИИ. Для каждого алерта — runbook.
- **Проверка устойчивости:** нагрузочный тест, специально устроенный сбой и постмортем по нему.
- **Деплой:** VPS через Ansible или Terraform, TLS на reverse proxy.

## 17. Этапы реализации

1. **Ядро:** вакансии, подбор вакансий по резюме и отклик через бота, скрининг по правилам, интерфейс рекрутера со входом, уведомления через outbox.
2. **Эксплуатация:** Docker, CI, метрики, трейсы, логи, SLO, деплой.
3. **Проверка ИИ** пограничных откликов.
4. **Уточняющие вопросы** с проверкой ответов ИИ.
5. **Заморозка и поиск повторных откликов.**
6. **Персональные данные:** согласие перед обработкой резюме, срок хранения, удаление по запросу кандидата.

После каждого этапа система должна оставаться рабочей.

## 19. Дальнейшее развитие: после успешного отбора

Сейчас воронка заканчивается решением рекрутера «Пригласить на созвон». Идеи для следующих версий, начиная с этого момента:

- **Запись на созвон:** рекрутер задаёт свободные слоты, кандидат выбирает время текстом в боте (кнопок нет), оба получают напоминания; позже — синхронизация с календарём.
- **Тестовое задание:** отправка задания через бота, приём решения с дедлайном, хранение в S3 и проверка рекрутером или техническим специалистом.
- **Этапы интервью:** настраиваемая цепочка этапов вакансии (созвон с HR → техническое интервью → финал) с оценкой и комментарием после каждого.
- **Оффер:** формирование и отправка оффера, ответ кандидата в боте, перевод в статус «Принят».
- **Передача в кадровую систему:** выгрузка данных принятого кандидата во внешнюю систему для оформления.
- **Аналитика воронки:** конверсия по этапам, время прохождения этапов, причины отказов — для рекрутеров и для настройки скрининга.

Идеи для подбора вакансий:

- **База кандидатов:** при создании вакансии показывать подходящих кандидатов из прошлых откликов и приглашать их через бота (нужно отдельное согласие на хранение резюме).
- **ИИ в подборе:** определять направление по резюме, чтобы не задавать вопрос, и искать вакансии, когда правила ничего не нашли.
